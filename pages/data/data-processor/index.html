Architecture overview

A scored, rate-limited pipeline for turning raw ledger data into fraud & risk signal

data-processor ingests uploaded general-ledger data, generates AI embeddings for every entry, runs a pluggable rules engine over them to produce risk and anomaly scores, and does all of it through a priority-aware, checkpointed task queue, so it survives crashes, doesn't starve small jobs behind large ones, and never overruns a model provider's rate limits.

02: Concurrency

Task queue & concurrency control

Three layered primitives, each generic enough to reuse outside this pipeline.

TaskQueue
Singleton job queue. Loads queued/in-progress tasks from Mongo on boot, refills itself as workers free up, caches source config per sourceKey.
WorkerQueue
Generic N-concurrent-worker limiter with an optional global rate cap and an onComplete hook, not specific to GL processing.
RequestQueue
Bounded-concurrency runner for a list of async items (default chunk size 4). Used inside the rules engine and the Bedrock client alike.
Priority split
Jobs ≥ 5,000 records are "low" priority, capped at 5 of the 10 total worker slots, so a handful of large jobs can never occupy every worker.

03: Reliability

Resumable, checkpointed processing

A crash or restart mid-task does not mean reprocessing the whole collection.

Precompute once, score in memory

Both RiskScoring and AnomalyDetection front-load their expensive aggregations in initialize(), before any row scoring starts, so per-row rule evaluation is pure in-memory lookup and math, never an additional DB round-trip.

Three precompute functions run once at the start of a task: _buildAmountStats() (per-GL-account mean/stdDev of amounts), _buildPairingCounts() (how often each account/counterparty pair occurs), and the windowed one below, each a single aggregation query, never repeated per row.

A single $setWindowFields aggregation computes, per document: how many entries the same user posted in a trailing 48h window, how many of those were near an approval threshold, and how many days since the same GL account was last touched.

05: Extensibility

Rules engine & registry

Rules are pure(-ish) functions, registered by key. Adding a new signal means adding one file, with no changes to the engine, processor, or scoring math.

Example: Benford's Law rule

"1" leads roughly 30% of naturally occurring amounts, "9" only ~4.6%, so an entry whose amount starts with a large digit (7, 8, 9) gets a higher suspicion score, capped at a modest confidence since it's a weak, population-level signal, not proof on its own.

rules/src/registry/risk-scoring/benfords-law/index.ts
// "1" leads ~30% of naturally occurring amounts, "9" only ~4.6% (Benford's Law)
evaluate = (row: any): RuleResult => {
    const firstDigit = this._firstSignificantDigit(Math.abs(row.amount ?? 0));
    let score = firstDigit >= 7 ? 0.6 + (firstDigit - 7) * 0.1   // rarest → most suspicious
              : firstDigit >= 5 ? 0.3 : 0.1;
    return { score, confidence: 0.5 };  // weak signal — confidence capped
};
06: Integration

AI / embeddings integration

A provider-agnostic AI layer, currently backed by AWS Bedrock, with per-model adapters and token-aware batching. The rate/token math behind this is detailed in the Algorithms tab.

Adapter pattern
Each embedding model (Titan, Cohere) owns its own request-building and response-parsing, so switching models never touches the calling code.
Centroid grouping
Embeddings can accumulate a running average vector per GL account or counterparty, published to SharedContext for anomaly detection.
Usage tracking
Token/record usage is upserted incrementally during processing: the billing trail for embedding spend.
Throttling-only retries
Retries trigger only on 429 / ThrottlingException, exponential backoff 2s → 32s.
07: Why it matters

Engineering highlights

  • Resumable by construction: a crash or restart resumes from the last checkpoint, not from zero, on collections that can run into hundreds of thousands of rows.
  • Fair scheduling: large jobs are capped to a subset of worker slots so they can never starve small, fast jobs behind them.
  • Provider-safe by default: per-model RPS and TPM limiters mean growth in usage degrades into backpressure, not throttling errors or runaway cost.
  • O(1) precompute, not O(n) queries: account stats, pairing counts, and windowed velocity metrics are computed once per task via aggregation pipelines.
  • Registry-based extensibility: a new fraud signal is one new file in the rules registry.
  • Full observability: every queue, batch, and token event is streamed live and logged (see the Observability tab).
08: In progress

Known hardening items

Confidence-scoring edge cases

Code review flagged a class of edge case across several rules: when a rule's required precomputed input is missing (e.g. no velocity data for a brand-new account), some early implementations reported a confident "no risk" (confidence: 1) rather than "unknown" (confidence: 0). The fix, treating missing precomputed data as low-confidence rather than as evidence of safety, is being applied consistently across the registry. Active hardening on a working pipeline, not a design gap.

Algorithms

The math behind never tripping a provider's rate limits

Two independent limiter types run per Bedrock model: one bounding request rate, one bounding token throughput, plus a deliberately pessimistic token estimator that stands in for a real tokenizer we don't have offline.

01: Request pacing

RateLimiter: sliding 1-second window

Caps how many requests can go out per second, and optionally enforces even spacing between them.

Algorithm: keep a list of timestamps for every request sent in the last 1,000ms. Before sending a new one, drop any timestamp older than 1 second ("evict"), then check if the remaining count is still under the cap.

  1. Evict timestamps older than now - 1000ms from the tracking list.
  2. If fewer than maxPerSecond timestamps remain, record now and proceed immediately.
  3. Otherwise, compute how long until the oldest timestamp exits the window (oldest + 1000ms - now) and wait that long before retrying.
  4. If minIntervalMs is set, also enforce a minimum gap since the last acquired call for even spacing, so requests aren't all bursted to the front of the window.

Why the minimum spacing matters: a naive sliding window lets all N requests fire in the first few milliseconds of a fresh window, then go silent: a burst pattern that trips provider-side burst protection even when the nominal RPS is respected. Enforcing a minimum interval (e.g. ~33ms for 30 RPS) spreads calls evenly across the whole second instead.

02: Throughput pacing

TokenWindowLimiter: sliding token-budget window

Same sliding-window idea as RateLimiter, but the unit being budgeted is tokens consumed, not requests sent, matching how providers actually meter LLM/embedding usage (TPM quotas).

  1. Evict any window entries older than windowMs (default 60s), subtracting their token counts from the running total.
  2. If the requested token count fits under the remaining budget, record it and proceed.
  3. If a single request is larger than the entire window budget, it can never "fit" under the normal rule, so it's let through alone, once the window is completely drained (usedInWindow === 0), instead of deadlocking forever.
  4. Otherwise wait until the oldest entry expires and re-check.
acquire(tokens) called
tokens ≤ maxTokensPerWindow
Normal path: proceed once usedInWindow + tokens ≤ max
tokens > maxTokensPerWindow
Oversized request: proceed only once the window is fully drained (usedInWindow === 0), then let it through alone
utilities/rate-limiter/token-window/index.ts
// A single request larger than the whole window budget can never "fit" normally;
// let it through alone once the window is fully drained instead of deadlocking.
const canProceed = fitsWithinWindowCap
    ? this._usedInWindow + tokens <= this._maxTokensPerWindow
    : this._usedInWindow === 0;

Each Bedrock model gets its own {'{'}rate, token{'}'} limiter pair, sized to that model's confirmed quota (maxRPS, tpmLimit × tpmSafetyMargin). A model without a confirmed quota falls back to a conservative shared pace (10 RPS, 90k tokens/minute) rather than silently borrowing another model's numbers.

03: Estimation

Token estimation: dual estimate, take the max

There's no maintained offline tokenizer for Cohere models: their own SDK only tokenizes via a network call, which would defeat the point of a pre-flight check. So the estimate is deliberately biased upward using two independent heuristics.

estimateTokenCount(text)
char-based estimate
text.length ÷ 3.3 chars/token
word-based estimate
wordCount × 1.4 tokens/word
Math.max(both, 1) → final estimate

Real BPE tokenizers average ~4 chars/token and ~0.75 tokens/word for English text. This estimator deliberately uses a smaller chars-per-token divisor (3.3) and a larger tokens-per-word multiplier (1.4) than reality, both biasing the result upward, then takes whichever estimate is bigger. That keeps the estimate safe for dense text like code or IDs (where char-based estimation would under-count) and safe for prose (where word-based estimation would under-count), at the cost of somewhat over-reserving token budget.

bedrock/src/utils/tokens/index.ts
const MIN_CHARS_PER_TOKEN = 3.3;
const MIN_TOKENS_PER_WORD = 1.4;

function estimateTokenCount(text: string): number {
    const charBasedEstimate = Math.ceil(text.length / MIN_CHARS_PER_TOKEN);
    const wordBasedEstimate = Math.ceil(wordCount * MIN_TOKENS_PER_WORD);
    return Math.max(charBasedEstimate, wordBasedEstimate, 1);
}
Closing the loop: TOKEN_ESTIMATE_CHECK

Bedrock returns the actual input token count in response headers. The system compares that against the pre-flight estimate and emits a TOKEN_ESTIMATE_CHECK observability event with the percentage difference (visible live on the dashboard), so estimator accuracy is measured against real traffic, not assumed.

04: Packing

Token-aware batching

Greedily packs texts into the fewest requests possible, bounded by both a max item count and a max estimated-token budget per request.

Algorithm (greedy bin-packing, single pass): walk the list of texts in order, accumulating them into the current batch. Flush (close out) the current batch and start a new one whenever adding the next text would either exceed the model's max item count or push the running token estimate over the per-batch token cap.

  • Only retries on throttling: HTTP 429, ThrottlingException, or TooManyRequestsException. Any other error (validation, auth, malformed request) fails immediately since retrying won't help.
